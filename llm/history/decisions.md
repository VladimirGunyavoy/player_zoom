## Decision #1: Dependency Injection вместо прямых импортов

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Циркулярные импорты при сложных зависимостях между менеджерами и компонентами.

```python
# ❌ Проблема:
# input_manager.py
from .zoom_manager import ZoomManager

# zoom_manager.py
from .scene_setup import SceneSetup

# scene_setup.py
from .input_manager import InputManager

# → Циркулярная зависимость!
```

**Рассмотренные варианты:**

1. **Прямые импорты** - не работает из-за циклов
2. **Отложенные импорты** (import внутри функций) - плохо для type hints
3. **Dependency Injection** - компоненты регистрируются после создания
4. **Event Bus** (pub/sub) - слишком сложно для песочницы

**Решение:** Dependency Injection (вариант 3)

**Реализация:**
```python
# Создаем менеджеры независимо
input_manager = InputManager()
zoom_manager = ZoomManager(...)

# Регистрируем зависимости после создания
input_manager.register_zoom_manager(zoom_manager)
```

**Type hints** через TYPE_CHECKING:
```python
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from .zoom_manager import ZoomManager  # только для IDE/mypy

class InputManager:
    def __init__(self):
        self.zoom_manager: Optional["ZoomManager"] = None
```

**Почему именно так:**
- ✅ Разрывает циркулярные зависимости
- ✅ Сохраняет type hints для IDE
- ✅ Явное управление зависимостями в main.py
- ✅ Гибкость - легко добавить новые зависимости
- ❌ Чуть больше boilerplate кода

**Альтернативы не выбраны:**
- Event Bus - overkill для небольшого проекта
- Отложенные импорты - теряем type hints

**Статус:** ✅ Активно используется

## Decision #2: Аффинное преобразование для зума

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Как реализовать зум с сохранением точки взгляда (invariant point)?

**Требования:**
- При зуме точка, на которую смотрит камера, должна оставаться на месте
- Все объекты сцены должны масштабироваться
- Математически корректно (без накопления ошибок)

**Рассмотренные варианты:**

1. **Простой зум** - масштабировать все объекты вокруг (0,0,0)
   - ❌ Точка взгляда сдвигается

2. **Перемещение камеры** - двигать камеру ближе/дальше
   - ❌ Меняется перспектива, не совсем "зум"

3. **Аффинное преобразование** - `x' = a*x + b` с вычислением b для сохранения точки
   - ✅ Математически корректно
   - ✅ Точка взгляда остается на месте

**Решение:** Аффинное преобразование (вариант 3)

**Математика:**

Условие сохранения точки `p`: `p' = p`

```
a*p + b = p
b = p - a*p = (1 - a)*p
```

При изменении зума на коэффициент `k`:
```
a_new = k * a_old
b_new = k * b_old + (1 - k) * p
```

где `p` - инвариантная точка (look point).

**Реализация:**
```python
def change_zoom(self, sign: int):
    inv_point = self.identify_invariant_point()  # вычислить p
    zoom_multiplier = self.zoom_fact ** sign     # k

    self.a_transformation *= zoom_multiplier
    self.b_translation = zoom_multiplier * self.b_translation + \
                         (1 - zoom_multiplier) * inv_point
```

**Почему именно так:**
- ✅ Математически строго корректно
- ✅ Нет накопления ошибок (трансформация к real_position)
- ✅ Работает для любой точки
- ✅ Обобщается на 3D (пока используется 2D на плоскости y=0)

**Альтернативы не выбраны:**
- Перемещение камеры - не дает эффект зума
- Простой зум - точка сдвигается

**Источник:** Курс линейной алгебры / компьютерной графики

**Статус:** ✅ Активно используется

## Decision #3: NumPy для математики

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Какую библиотеку использовать для векторных операций?

**Рассмотренные варианты:**

1. **Ursina Vec3** - встроенный в движок
2. **NumPy** - стандартная библиотека для научных вычислений
3. **Чистый Python** (списки/кортежи)

**Решение:** NumPy (вариант 2)

**Почему:**
- ✅ Привычный инструмент для математики
- ✅ Хорошая документация и community
- ✅ Богатый API (sin, cos, tan, radians, etc.)
- ✅ Эффективно для массовых операций
- ❌ Дополнительная зависимость

**Альтернативы не выбраны:**
- Vec3 - менее удобен для тригонометрии
- Чистый Python - слишком verbose

**Пример использования:**
```python
import numpy as np

psi = np.radians(player.rotation_y)
phi = np.radians(camera.rotation_x)

d = h / np.tan(phi)
dx = d * np.sin(psi)
dz = d * np.cos(psi)
```

**Статус:** ✅ Активно используется

## Decision #4: Scalable pattern

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Как обеспечить что все объекты корректно масштабируются при зуме?

**Требования:**
- Трансформация должна применяться к **оригинальным** значениям
- Простота добавления новых объектов

**Рассмотренные варианты:**

1. **Вручную** - вызывать трансформацию для каждого объекта
   - ❌ Легко забыть
   - ❌ Дублирование кода

2. **Базовый класс Scalable** - наследование от Entity + apply_transform()
   - ✅ Автоматическая поддержка
   - ✅ Единое место для логики

3. **Component pattern** - добавлять ScalableComponent к Entity
   - ✅ Гибко
   - ❌ Сложнее для простого случая

**Решение:** Базовый класс Scalable (вариант 2)

**Реализация:**
```python
class Scalable(Entity):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.real_position = np.array(self.position)
        self.real_scale = np.array(self.scale)

    def apply_transform(self, a, b):
        self.position = self.real_position * a + b
        self.scale = self.real_scale * a
```

**Использование:**
```python
class MyFloor(Scalable):
    pass  # автоматически поддерживает зум

floor = MyFloor(...)
zoom_manager.register_object(floor)  # готово!
```

**Почему именно так:**
- ✅ Простота использования
- ✅ Невозможно забыть реализовать apply_transform
- ✅ Единое место для логики трансформации
- ❌ Наследование вместо композиции (но для простого случая ОК)

**Ключевая идея:**
Сохранять `real_position` и `real_scale` - **оригинальные** значения. Трансформация всегда применяется к ним, а не к текущим значениям. Это предотвращает накопление ошибок.

**Статус:** ✅ Активно используется

## Decision #5: Print вместо Logging

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Как делать debug вывод?

**Рассмотренные варианты:**

1. **print()** - встроенная функция Python
2. **logging** - стандартная библиотека logging
3. **Сторонняя библиотека** (loguru, structlog)

**Решение:** print() (вариант 1)

**Почему:**
- ✅ Это песочница, не production код
- ✅ Простота - не нужна настройка

**Философия:**
Простота > профессионализм для исследовательского проекта.

**Когда пересмотреть:**
Если проект вырастет в production или debug станет сложным.

## Decision #6: Watcher для auto-reload

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
При каждом изменении кода нужно вручную перезапускать программу.

**Рассмотренные варианты:**

1. **Ручной перезапуск** - Ctrl+C → python main.py
2. **Watchdog** - библиотека для отслеживания изменений файлов
3. **Встроенный механизм Ursina** - ?

**Решение:** Watchdog (вариант 2)

**Реализация:**
```
run.py → watcher.py → запускает main.py → при изменении .py → перезапуск
```

**Логика:**
- Exit code 0 (нормальный выход) → автоматически перезапустить
- Exit code != 0 (ошибка) → остановиться (дать исправить)
- Ctrl+C → остановить watcher

**Почему именно так:**
- ✅ Ускоряет итерации разработки
- ✅ Не перезапускает при ошибках (чтобы прочитать traceback)
- ✅ Watchdog - надежная библиотека
- ❌ Дополнительная зависимость

**Альтернатива:** nodemon для Python - но watchdog достаточно.

**Статус:** ✅ Активно используется в разработке

## Decision #7: Структура llm/ для контекста

**Дата:** 2026-03-19

**Проблема:**
При работе через несколько диалогов с AI агентами:
- Теряется контекст проекта
- Приходится заново объяснять архитектуру
- Большое потребление токенов на передачу контекста

**Требования:**
- Минимизировать токены
- Сохранить адекватность контекста
- Структурированность и навигация

**Рассмотренные варианты:**

1. **Плоская структура** (все файлы в llm/)
   - Простота
   - ❌ Сложно навигировать при росте

2. **Вложенная структура** (context/, state/, history/)
   - ✅ Четкое разделение ответственности
   - ✅ Масштабируемость
   - Чуть сложнее

3. **Git-подобная** (.llm/refs/, .llm/objects/)
   - ❌ Overkill

**Решение:** Вложенная структура (вариант 2)

```
llm/
├── context/      # Редко меняется, базовые знания
├── state/        # Часто меняется, текущее состояние
└── history/      # Append-only, история
```

**Ключевые файлы:**
- `AGENT_START.md` - напутствие (читать первым!)
- `AGENT_END_ROUTINE.md` - чеклист завершения работы
- `context/start_prompt.md` - TL;DR + ключевые концепции
- `state/current.md` - что работает/не работает сейчас

**Принципы:**
- **Краткость** - TL;DR сначала, детали потом
- **Актуальность** - state/ обновляется каждую сессию
- **История** - history/ append-only
- **Навигация** - четкие ссылки между файлами

**Почему именно так:**
- ✅ Минимизирует токены (агент читает только нужное)
- ✅ Структурировано (легко найти информацию)
- ✅ Масштабируемо (легко добавлять новые файлы)
- ✅ Разделение по частоте изменений

**Inspiration:**
- Git (.git/ структура)
- Conventional Commits
- Project documentation best practices

**Статус:** ✅ Создано 2026-03-19
